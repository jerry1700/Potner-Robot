## 0. 이 프로젝트가 무엇인가

**Potner**(Pot + Partner)는 SSAFY 팀 프로젝트로 만드는 반려식물 로봇입니다.
화분을 얹고 다니면서 식물 상태를 스스로 살피고, 필요하면 급수·일광욕·충전
스테이션으로 알아서 이동하고, 사용자가 집에 오면 마중 나가 인사하고,
화면으로 표정을 짓고, 스피커로 말을 합니다.

프로젝트는 네 부분으로 나뉘고, 이 저장소 하나에 각자 브랜치로 들어가
있습니다.

| 부분 | 담당 기기 | 브랜치 |
|---|---|---|
| **로봇** (이 문서가 다루는 부분) | Jetson Orin Nano | `Robot-master` / `Robot-develop` |
| 스테이션 | Raspberry Pi 5 | `Raspberry-master` |
| 서버 | (클라우드) | `Server-master` |
| 앱 | 사용자 휴대폰 | `App-master` |

네 부분은 서로 직접 연결돼 있지 않습니다. 전부 **서버를 거쳐** 통신합니다.
예를 들어 사용자가 앱에서 "귀가 알림"을 보내면, 그건 로봇에 직접 가는 게
아니라 서버로 갔다가 서버가 로봇에 명령을 내려보내는 식입니다. 그래서
로봇 파트만 고쳐서 될 일과, 서버·앱 팀과 같이 정해야 할 일이 자주 섞입니다
(아래 "서버·앱 팀에 요청해 둔 것" 참고).

## 1. 로봇 하드웨어가 어떻게 나뉘어 있는가

로봇 안에는 컴퓨터가 두 대 있습니다. 왜 하나가 아니라 둘인지 아는 게
나중에 여러 코드를 이해하는 데 도움이 됩니다.

- **Jetson Orin Nano** — 로봇의 "두뇌"입니다. 카메라로 사람과 마커를
  찾고, 라이다로 지도를 만들고, 조도·수분 센서를 읽고, 서버와 통신하고,
  화면에 표정을 그리고, 스피커로 말합니다. 리눅스(우분투)가 돌아갑니다.
- **ESP32** — 모터만 전담하는 작은 마이크로컨트롤러입니다. 바퀴에 달린
  엔코더는 1초에 수천 번씩 신호를 보내는데, 리눅스는 이런 실시간 신호를
  정확한 타이밍으로 처리하는 데 약합니다(다른 프로그램 때문에 잠깐씩
  밀릴 수 있음). 그래서 모터 속도 제어(PID)와 엔코더 읽기는 ESP32 가
  전담하고, Jetson 은 ESP32 에게 USB 시리얼로 "왼쪽 이만큼, 오른쪽
  이만큼 속도로 가"라고 명령만 보냅니다.
- **배터리 두 개** — Jetson 용 4S 팩과 모터용 3S 팩이 분리돼 있습니다.
  Jetson 은 항상 전력을 쓰고 모터는 움직일 때만 쓰기 때문에, 실사용에서는
  Jetson 팩이 먼저 바닥납니다. 그래서 배터리 잔량은 Jetson 팩만 잽니다
  (모터팩 고갈은 따로 감지하지 못합니다 — 알고 있어야 할 부분입니다).

자세한 배선도는 [`README.md`](../README.md) 의 "시스템 구성"에 있습니다.

## 2. 소프트웨어가 어떻게 짜여 있는가

Jetson 쪽 소프트웨어는 **ROS 2**(로봇 프로그램들이 서로 통신하도록 도와주는
프레임워크)로 짜여 있습니다. 잠깐만 짚고 넘어가겠습니다.

- 하나의 실행 단위를 **노드**라고 부릅니다. 예를 들어 카메라 영상을
  처리하는 노드, 모터에 명령을 보내는 노드가 각각 따로 있습니다.
- 노드끼리는 **토픽**이라는 이름표가 붙은 채널로 데이터를 주고받습니다.
  한 노드가 토픽에 값을 "발행"하면, 그 토픽을 "구독"하는 다른 노드들이
  값을 받습니다. 예를 들어 `plant/lux` 토픽에 조도 센서 노드가 값을
  발행하면, 임무를 판단하는 노드가 그걸 구독해서 씁니다.
- 이 저장소의 루트가 곧 **colcon 워크스페이스**입니다. `colcon build`
  로 빌드하고 `ros2 launch`/`ros2 run` 으로 노드를 띄웁니다.

### 패키지 구성 (`src/` 아래)

| 패키지 | 역할 |
|---|---|
| `potner_base` | Jetson ↔ ESP32 통신, 바퀴 움직임 계산, 화면 표정, 센서 읽기 |
| `potner_perception` | 카메라로 사람 인식(YOLO), 스테이션 마커 인식(ArUco) |
| `potner_docking` | 마커를 보면서 스테이션에 정밀하게 붙는 제어 |
| `potner_mission` | 서버 명령(이동·귀가)을 실제 움직임으로 바꾸고 결과를 회신, 최우선 안전 정지. 임무를 스스로 판단하지는 않습니다 — 그건 서버가 합니다 |
| `potner_bridge` | 서버와 통신하는 다리 역할 (아래 3절 참고) |
| `potner_description` / `potner_bringup` | 로봇 3D 형상 정의, 실행 설정 모음 |
| `potner_msgs` | 노드 사이에서 주고받는 메시지 형식 정의 |
| `potner_firmware` | ESP32 에 올라가는 펌웨어 (ROS 패키지 아님, PlatformIO) |
| `potner_llm` | 대화·페르소나 담당 — **LLM 파트 팀원 소유, 상의 없이 수정 금지** |

`tests/` 에는 ROS 없이 돌아가는 순수 로직 테스트가 있습니다. `docs/` 에는
이 문서를 포함한 명세·환경 문서들이 있습니다.

### 왜 계산 로직을 노드 파일 밖으로 빼두었나

바퀴 속도 계산, 마커 위치 계산 같은 순수한 계산 부분은 ROS 에 의존하지
않는 별도 파일(예: `kinematics.py`)로 분리해 두었습니다. ROS 가 설치된
Jetson 이 없어도, 노트북이나 CI 서버에서 `pytest` 로 이 계산이 맞는지
검증할 수 있게 하려는 것입니다. 실제로 계산 로직을 노드 파일 안에 넣어
뒀다가 CI 가 못 잡는 버그를 두 번 냈던 적이 있어서(카메라 초점거리 계산이
거꾸로 되어 있던 것, 마커 각도 계산에 필요한 보정 하나가 빠져 있던 것)
이후로는 규칙으로 정했습니다.

## 3. 로봇이 서버와 어떻게 통신하는가 (MQTT)

로봇과 서버는 인터넷을 거쳐 떨어져 있는 사이라, ROS 토픽으로 직접 통신할
수 없습니다. 대신 **MQTT** 라는 별도 프로토콜을 씁니다. 짧게 설명하면:

- 메시지를 주고받는 **브로커**라는 중계 서버가 하나 있고, 로봇과 서버
  둘 다 여기에 접속합니다.
- MQTT 에도 ROS 와 비슷하게 **토픽**이 있고, 계정마다 어떤 토픽을
  읽고 쓸 수 있는지 정해주는 규칙을 **ACL**이라고 부릅니다. 우리 로봇
  계정은 `potner/device/jetson-01/...` 로 시작하는 자기 토픽만 건드릴
  수 있습니다.
- `potner_bridge` 패키지가 ROS 토픽 값을 MQTT 메시지로 바꿔 보내고,
  반대로 서버가 보낸 MQTT 명령을 ROS 토픽으로 바꿔 다른 노드에
  전달합니다. 그래서 이름이 "다리(bridge)"입니다.

메시지 형식(어떤 값을 어떤 토픽으로 보내야 하는지)은 서버 팀이 관리하는
[`DEVICE-JETSON.md`](DEVICE-JETSON.md)(젯슨이 할 일) /
[`DEVICE-MQTT.md`](DEVICE-MQTT.md)(공통 계약과 설계 근거) 가 기준이고,
로봇 쪽 구현 메모는 [`MQTT_CONTRACT.md`](MQTT_CONTRACT.md) 에 있습니다.
서버 저장소(`Server-develop`)에서 가져온 사본이라, 서버 팀이 갱신하면
다시 받아와야 합니다.

**ACL 규칙에서 벗어난 발행은 브로커가 에러 없이 조용히 버립니다.** 로그도
안 남습니다. "MQTT는 연결됐다는데 값이 서버에 안 들어온다"는 증상이
보이면 이것부터 의심하세요.

## 4. 저장소 규칙 — 브랜치와 티켓

이 팀은 지라(Jira)로 작업 티켓을 관리하고, **브랜치 이름에 티켓 번호가
반드시 들어갑니다.**

```
Robot-<종류>/<작업 내용>/<티켓번호>
예)  Robot-feature/greet-on-arrival/351
     Robot-fix/mqtt-broker-integration/291
```

작업 흐름은 `Robot-develop` 에서 새 브랜치를 파서 작업하고, 끝나면
`Robot-develop` 에 머지하고, 거기서 다시 `Robot-master` 로 머지합니다.
**티켓 번호 없이는 브랜치를 만들지 마세요** — 나중에 이 커밋이 어떤
작업인지 추적할 방법이 사라집니다.

## 주의사항 — 먼저 읽어주세요

### 1. 모터 첫 배선 (다음에 할 큰 작업)

로봇이 아직 실제로 움직여본 적이 없습니다. 지금까지는 센서·통신·화면 쪽만
검증됐고, 모터 배선과 첫 주행이 다음 단계입니다. 장치별 핀·배선은
[`WIRING.md`](WIRING.md) 에 정리해 뒀습니다.

- 반드시 `Robot-feature/motor-bringup/349` 브랜치에서 시작합니다. 개루프
  명령과 확인 도구(`tools/motor_bringup.py`)가 이 브랜치에만 있습니다.
  바퀴 지름(60mm) 자체는 이미 `Robot-develop` 에 반영돼 있습니다.
- 349 는 `Robot-develop` 의 최근 커밋들을 받지 못한 상태입니다. 배선을
  시작하기 전에 `git rebase Robot-develop` 로 최신 상태로 맞춰두는 것을
  권합니다.
- 첫 회전은 **개루프**(`D` 명령)로 확인합니다. 개루프는 엔코더 값을
  보지 않고 정해진 세기로만 모터를 돌리는 방식이고, **폐루프**(`V`
  명령)는 엔코더로 실제 속도를 재서 목표 속도에 맞게 자동으로
  세기를 조절하는 방식입니다. 폐루프는 엔코더 배선이 잘못돼 있으면
  "속도가 안 나온다"고 착각해서 세기를 계속 최대로 올리다가 바퀴가
  갑자기 전속력으로 돌 수 있습니다. 개루프는 이 위험이 없어서 배선을
  처음 확인할 때 씁니다.
- 바퀴는 공중에 띄운 채로 확인합니다. 배선 방향이 반대면 로봇이 책상
  아래로 떨어질 수 있습니다.
- 모터 드라이버(BTS7960)의 `R_EN`, `L_EN` 핀은 3.3V 에 연결합니다.
  연결하지 않으면 PWM 신호를 보내도 모터가 돌지 않습니다. 첫 시험에서
  가장 자주 걸리는 부분입니다.
- 모터 전류가 흐르는 선(B+/B−/M+/M−)은 브레드보드에 올리지 않습니다.
  브레드보드 접점은 1A 정도까지만 버팁니다. 나사 단자로 직접 연결하고,
  배터리 쪽 플러스(+) 선에는 인라인 퓨즈 홀더로 퓨즈를 직렬로 넣습니다.
  배터리(또는 BMS 출력)에 최대한 가깝게 넣어야 그 뒤 배선 전체가
  보호됩니다. 용량은 잠정적으로 README 의 15A 지연형(slow-blow) 을
  따르되, FIT0403 의 실제 기동전류와 배선 굵기를 확인한 뒤 다시 정하는
  것을 권합니다 (아직 실측 안 됨).
- 배터리팩에 BMS(과충전·과방전 보호 회로)가 내장돼 있는지 먼저
  확인합니다. 열수축 튜브 안에 작은 기판이 보이고 밖으로 나온 선이
  2~3가닥뿐이면 이미 연결된 것이라 추가 배선이 필요 없습니다. 셀과
  BMS 모듈을 따로 샀다면 직접 배선해야 하는데, 밸런스 커넥터 순서를
  틀리면 셀이 단락될 수 있으니 꽂기 전에 멀티미터로 전압을 재서
  확인하세요 (B0-B1 ≈ 3.7V, B0-B2 ≈ 7.4V, B0-B3 ≈ 11.1V).
- 배선 전에 멀티미터로 먼저 확인합니다: 배터리 팩 전압(11.1~12.6V),
  FIT0403 모터의 모터 선 한 쌍(저항이 수 옴으로 낮게 나옵니다), 엔코더가
  3.3V 에서 정상 동작하는지 (ESP32 의 GPIO 34~39 핀은 3.3V 이상을 견디지
  못합니다).
- 확인 도구로 `tools/motor_bringup.py` 를 씁니다. ROS 를 띄우지 않고
  ESP32 에 직접 명령을 보내서, 모터·엔코더·통신 중 어디가 문제인지
  구분해서 알려줍니다.

### 2. 한 번 겪은 문제들

작업하다 실제로 걸렸던 것들입니다. 같은 데서 또 막히지 않도록 남겨둡니다.

| 문제 | 원인과 대처 |
|---|---|
| 센서 배선 후 소손 | 표만 보고 배선하지 말고 보드에 인쇄된 라벨을 직접 확인 |
| MQTT 로 보낸 값이 서버에 안 들어감 | 위 3절 참고. ACL 규정에 안 맞는 발행은 에러 없이 조용히 버려집니다 |
| 센서값이 서버에 일부만 반영됨 | 메시지마다 붙는 고유 번호(`messageId`)를 재사용하면 서버가 중복으로 보고 버립니다. 발행마다 새로 만들어야 합니다 |
| 화면이 꺼진 채로 안 돌아옴 | 젯슨 화면 절전 기능과 그래픽 드라이버가 충돌해서 검은 화면이 됩니다. 절전은 이미 꺼둔 상태입니다. 화면을 새로 세팅할 경우 [`JETSON_DISPLAY.md`](JETSON_DISPLAY.md) 참고 |
| 화면 케이블을 전원 켠 채로 뽑아서 복구 안 됨 | 케이블을 먼저 연결하고 전원을 켤 것. 시연 중에는 화면 케이블을 건드리지 않기 |
| 젯슨 터미널에 여러 줄 붙여넣으면 중간 줄이 잘림 | 명령은 한 줄로 보내기 |
| 빌드했는데 코드가 안 바뀐 것처럼 동작함 | 소스 코드가 아니라 예전에 빌드해둔 실행 파일이 실행되고 있을 수 있습니다. 안 되면 `rm -rf build install` 후 재빌드 |
| 조도·수분 센서(I2C)가 계속 인식 안 됨 | 센서 탐지 방식(`write_quick`)이 Jetson 에서 지원되지 않습니다. `read_byte` 로 탐지 (`plant_sensors_node._probe` 참고) |
| 조도 센서(BH1750) 값이 항상 0 | 측정 전마다 전원 켜기 명령이 필요합니다. 코드에는 이미 반영돼 있습니다 |
| `.bashrc` 에 줄을 추가했더니 기존 줄에 붙어버림 | 파일 마지막 줄에 개행이 없던 것이 원인입니다. `printf '\n...'` 로 추가 |

### 3. 예전과 달라진 동작

- **로봇이 더 이상 스스로 임무를 판단하지 않습니다.** 예전에는
  `mission_manager`가 센서 임계값(배터리·수분·조도·온도)을 직접 보고
  급수·충전·일광욕 이동을 스스로 결정했습니다(`priority.py`). 이제 그
  판단은 전부 서버가 합니다 — 서버가 생육 데이터를 보고 결정해서
  `command/navigate`로 명령을 내리면, 로봇은 그 좌표로 이동·도킹하고
  결과만 회신합니다(`result/navigate`). **`priority.py`는 삭제됐고**,
  로봇 설정에는 이제 목적지 좌표도 임계값도 없습니다. 코드에서
  `Thresholds`, `StationMarker`, `evaluate()` 같은 걸 찾고 계셨다면
  없는 게 맞습니다 — `navigate_contract.py`/`navigate_session.py`를
  대신 보세요. 확인 절차는 [`NAVIGATE_TEST.md`](NAVIGATE_TEST.md).
- 로봇은 이제 **귀가 명령을 받아야만** 인사합니다. 예전에는
  카메라에 사람이 보이기만 하면 인사했는데, 그러면 집에 있던 가족이
  지나가도 인사하는 문제가 있었습니다. 지금은 서버의 `welcome_start`로
  GREETING에 도착한 뒤에만 인사 대기가 열립니다. 카메라 앞에 서도 반응이
  없다면 고장이 아니라 아직 GREETING 도착 전이거나 대기시간이 끝난 것입니다.
  시험 절차는 [`ARRIVAL_TEST.md`](ARRIVAL_TEST.md)를 따르세요.
- CI(자동 테스트 서버) 설정을 바꿨습니다 (`requirements_ci.txt` 추가,
  불필요한 패키지 설치 제거). **아직 젠킨스 빌드 결과를 확인하지
  못했습니다** — 다음에 붙는 사람이 제일 먼저 확인해야 할 항목입니다.
- 표정 수신 로그(`mqtt_bridge_node`의 "표정 수신: ...")가 **120초에
  한 번만 찍힙니다.** 값이 실제로 바뀌었는지와 무관하게 시간 간격으로만
  걸려 있어서, 그 사이에 온 값은 로그에 안 남을 수 있습니다. 진단할
  때는 이 로그 대신 `ros2 topic echo /display/expression`으로 실제
  토픽을 보세요. 아직 코드로 고치지 않은 알려진 문제입니다.

### 4. 비밀값

- 비밀번호나 토큰 같은 값은 저장소나 문서 어디에도 적어두지 않습니다.
  주소나 ID 같은 설정값만 저장소에 있고, 비밀값은 젯슨의 `~/.bashrc`
  파일 안 환경변수에만 있습니다.
- 사람에게 전달할 때는 메신저 개인 대화로 합니다. 파일로 모아두거나
  공개 채널에 올리지 않습니다 — 예전에 화면을 그대로 붙여넣다 값이
  노출된 적이 있습니다.
- 지금 쓰는 MQTT 비밀번호는 한 번 노출됐던 값이라, 시연 전에 서버팀과
  함께 교체하는 것을 권합니다.

## 서버·앱 팀에 요청해 둔 것

로봇 파트만으로는 못 끝내고, 서버·앱 팀과 같이 정해야 하는 것들입니다.

1. **NAVIGATE 전용 타임아웃** — 서버가 급수·촬영·송풍·이동에 같은
   제한시간(120초) 하나를 씁니다. 이동은 도킹까지 포함해 더 걸릴 수
   있습니다. 늦은 회신도 서버가 받아 체인을 잇지만 이력에 `TIMED_OUT`
   이 남습니다. 실측해서 자주 넘기면 이동만 늘려 달라고 요청하세요.
   (`command/navigate` 수신과 `result/navigate` 회신은 구현 완료 —
   [`NAVIGATE_TEST.md`](NAVIGATE_TEST.md) 참고)
2. **`command/speech`** — 서버의 LLM(대화 담당 AI)이 만든 문장을 로봇에게
   전달할 경로가 아직 명세에 없습니다. 지금은 로봇이 정해진 인사말만
   말합니다.
3. **조도 센서 위치 정정 전달** — `DEVICE-JETSON.md`에 조도 센서가 아직
   스테이션(라즈베리)에 있다고 적혀 있고, 젯슨으로 옮기는 걸 검토 항목으로
   남겨뒀습니다. **실제로는 처음부터 BH1750이 젯슨에 있고, 이미
   `jetson-01`이 `ILLUMINANCE`를 보내고 있습니다.** 서버팀에 이미 끝난
   일이라고 알려줘야 문서가 정확해집니다.

## 설계 규칙

1. 계산 로직은 ROS 에 의존하지 않는 별도 모듈로 분리합니다 (2절 참고).
   ROS 없이도 테스트 서버에서 검증할 수 있는 유일한 방법이고, 노드
   안에 로직을 넣어뒀다가 버그를 두 번 놓친 적이 있습니다. 세부 규칙은
   [`CODE_STYLE.md`](CODE_STYLE.md) 참고.
2. 같은 값이 여러 곳에 흩어져 있을 때(설정 파일, 노드 기본값, 계산
   모듈, ESP32 펌웨어 상수) 이 값들이 서로 일치하는지 비교하는 테스트가
   있습니다. 이 테스트가 실패하면 테스트를 고치지 말고, 값이 어긋난
   쪽을 고칩니다.
3. `src/potner_llm/` 과 `voice-chat-server/` 는 LLM 파트가 관리합니다.
   상의 없이 수정하지 않습니다. 스피커 담당 노드(`speaker_node`)는
   `shell=True` 를 쓰지 않습니다 — 여기 들어오는 문장은 LLM 이 만든
   외부 입력이라, 잘못된 문장으로 시스템 명령을 실행시킬 위험이 있기
   때문입니다.
