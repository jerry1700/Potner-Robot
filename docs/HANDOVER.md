## 2. ★ 넘겨받은 날 바로 알아야 할 것

**CI 가 실제로는 돌지 않습니다.** `Jenkinsfile` 이
`pip install -r requirements_ci.txt` 를 하는데 **그 파일이 저장소에 없습니다**
(이력에도 없음). Setup 단계에서 죽으므로 "테스트는 CI 가 잡는다"는 주석들은
현재 로컬 `pytest tests/` 에만 해당합니다. `requirements.txt` 는 젯슨 전용
패키지(`Jetson.GPIO`, `cuda-toolkit`)가 섞여 있어 CI 에 못 씁니다 — CI 용
최소 목록(numpy, opencv-python-headless, pyyaml, paho-mqtt, pytest)을 분리해
만드는 것이 첫 작업으로 적당합니다.

**젯슨이 feature 브랜치에 체크아웃되어 있을 수 있습니다.** 마지막 작업이
`Robot-feature/display-expression/300` 이었습니다. 시작 전에:

```bash
cd ~/potner_ws && git checkout Robot-develop && git pull
colcon build && source install/setup.bash
```

**모터 브링업 선행 작업이 커밋되지 않은 채 있습니다.** 개발 PC 의 git stash
(`stash@{0}`) 에 펌웨어 수정(바퀴 지름 0.065→0.075, 개루프 D 명령, V4 보드
설정)과 벤치 도구(`tools/motor_bringup.py`)가 들어 있습니다. **stash 는 그
PC 에만 존재합니다.** 티켓을 만들어 브랜치로 올리기 전에는 다른 곳에서 보이지
않습니다. 현재 트리의 펌웨어는 바퀴 지름이 0.065 로 틀린 상태입니다(실제
75mm).

## 3. 환경·자격증명 — 어디에 있나

**비밀값은 저장소 어디에도 적혀 있지 않습니다.** 이 문서에도 없습니다.
비밀이 아닌 설정값(주소·계정명·ID)은 저장소가 기억하고, 비밀값은 **기계의
환경변수**(젯슨 `~/.bashrc`)에만 둡니다. 사람 간 전달은 MM 개인 DM 같은
비공개 채널로 하고, 파일로 모아두거나 공개 채널에 올리지 마세요 — 실제로
`.bashrc` 를 화면에 붙여넣다 비밀번호가 노출된 적이 있습니다. 토큰류는
보관하지 않습니다: 로그인 토큰은 만료되면 새로 받고, GitLab PAT 는 개인별
발급이라 인수인계 대상이 아닙니다.

| 항목 | 위치 |
|---|---|
| MQTT 비밀번호 | 젯슨 `~/.bashrc` 의 `POTNER_MQTT_PASSWORD`. 원본은 서버의 `infra/mosquitto/config/password.txt` (서버 팀) |
| MQTT 계정 | `jetson-01` — **`device_id` 와 반드시 같아야 함** (ACL `%u` 치환) |
| 브로커 | `i15e104.p.ssafy.io:1884` (1883 아님) |
| REST API | `http://i15e104.p.ssafy.io/api/v1` — 앱 로그인 토큰 필요 |
| plantId / robotId | `4e20f51f-b9b4-4cf2-90ee-233ad4cf2950` / `59d829a7-2f0f-4842-ae4c-de41e1fe4fa5` |
| 젯슨 GitLab 인증 | `read_repository` 전용 PAT (젯슨은 pull 만) |

도달 확인은 로그가 아니라 REST 로 합니다 — 하트비트·배터리는 성공해도 서버
로그에 안 남습니다:

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  http://i15e104.p.ssafy.io/api/v1/plants/4e20f51f-b9b4-4cf2-90ee-233ad4cf2950/devices
# connectionStatus / batteryMeasuredAt / currentState 를 봅니다
```

⚠️ 알려진 숙제: 지금 비밀번호는 한 번 화면에 노출된 적이 있습니다. 시연 전에
서버 팀과 함께 교체하는 것이 좋습니다 (브로커 쪽도 같이 바꿔야 함).

## 4. 다음 큰 산 — 모터 브링업

부품: 3S BMS · BTS7960 ×2 · FIT0403 ×2 · ESP32 DevKitC V4. **아직 배선
자체를 안 했습니다.** 순서와 이유:

1. **전원 없이 측정부터.** 팩 전압(11.1~12.6V), FIT0403 여섯 선 구분(모터
   권선 한 쌍만 저항이 수 Ω), **엔코더가 3.3V 에서 동작하는지** (A 출력이
   0↔3.3V 로 오가는지). 마지막 것에 따라 레벨 시프터 필요 여부가 갈립니다.
   GPIO 34~39 는 3.3V 한계이고 내부 풀업이 없습니다.
2. **첫 회전은 개루프(D 명령)로.** 스태시의 펌웨어에 들어 있습니다. 이유:
   엔코더 배선이 틀린 채 폐루프(V 명령)를 돌리면 적분항이 차올라 **바퀴가
   전속으로 돕니다.** 개루프는 엔코더와 무관하고 듀티 상한 0.5 로 묶여
   있습니다.
3. **바퀴는 공중에.** 방향이 반대로 배선돼 있으면 책상에서 떨어집니다.
4. `R_EN`·`L_EN` 을 3.3V 에 묶어야 합니다. 펌웨어가 이 핀을 안 건드려서, 안
   묶으면 PWM 을 보내도 모터가 안 돕니다 — 첫 시험에서 가장 흔한 막힘.
5. 모터 전류(B+/B−/M+/M−)는 **브레드보드에 올리지 말 것** (접점 한계 ~1A).
   나사 단자 직결. 배터리 라인에는 5A 퓨즈.
6. 검증 도구는 `tools/motor_bringup.py` (스태시). 통신·엔코더·모터 문제를
   갈라서 알려줍니다.

이게 끝나면 312(오도메트리) → 241(SLAM 지도) → 36·37·50·130·131 → 44 가
차례로 풀립니다. **로봇 파트 잔여 티켓의 절반이 이 뒤에 줄 서 있습니다.**

## 5. 서버 팀 답변 대기 중

`DEVICE-MQTT.md` 12절에 서버 팀이 하드웨어 팀에게 물은 질문 7개가 있습니다.
그중 두 개가 우리 코드를 막고 있습니다:

- **`commandId` 왕복** (12절 3번, 서버 팀이 가장 중요 표시). 없으면 서버가
  "명령 직전의 IDLE"과 "도착 후의 IDLE"을 구분 못 해 **대기 장소의 로봇에게
  급수 명령을 보내 물을 쏟습니다.** 서버가 주기로 하면 `DockToStation` 액션에
  실어 상태 보고에 되돌리면 됩니다.
- **`command/speech`** — TTS 대사를 받을 토픽이 명세에 없습니다. ACL 이
  `command/#` 만 읽기 허용하므로 그 아래로 요청해 둔 상태. 이게 없으면
  `speaker_node` 는 mission_manager 의 인사말만 말합니다.

브로커의 특성 하나는 꼭 기억하세요: **ACL 위반 발행은 조용히 버려집니다.**
에러도, 서버 로그도 없습니다. "연결됐는데 값이 안 들어온다" 싶으면
`docs/MQTT_CONTRACT.md` 의 ACL 절부터 보세요.

## 6. 설계 규칙 — 왜 이렇게 생겼나

**계산 로직은 rclpy 를 import 하지 않는 순수 모듈에 둡니다.** CI(ROS 없음)가
검증할 수 있는 유일한 방법이고, 실제로 두 번 당했습니다 — 초점거리 공식이
뒤집힌 채(410px vs 876px), yaw 정규화가 빠진 채(-173° 유출) 노드 파일 안에
있어서 테스트가 못 잡았습니다. 노드 파일은 구독·발행·타이머만 갖습니다.

**드리프트 가드 테스트가 세 겹 있습니다.** yaml ↔ 노드 기본값 ↔ dataclass
(`test_config_consistency.py`), MissionState ↔ 서버 enum, 펌웨어 상수 ↔
파이썬(스태시의 `test_firmware_constants.py`). 값을 한 곳만 고치면 이
테스트들이 잡습니다. **잡히면 테스트를 고칠 게 아니라 나머지 곳을 마저
고치는 것입니다.**

**스타일은 [`CODE_STYLE.md`](CODE_STYLE.md) 6개 규칙이 전부입니다.** 현재
로봇 파트 파일은 전부 준수 상태입니다.

**`src/potner_llm/` 과 `voice-chat-server/` 는 LLM 파트 팀원 소유입니다.**
스타일 규칙을 적용하지 않았고 앞으로도 그쪽 파트와 상의 없이 고치지 마세요.
(예: 그쪽의 `logger.info("%s", x)` 는 logging 모듈의 지연 서식으로 의도가
있는 패턴입니다.)

**speaker_node 는 절대 `shell=True` 를 쓰면 안 됩니다.** TTS 문장이 서버
LLM(외부 입력)에서 오므로 명령은 argv 리스트로만 조립합니다.
